# v0.6.1 Guarded LLM Report Drafting with Explicit Safety Trace

## 定位

v0.6.1 在 v0.6.0 的 evidence-bottleneck case report prototype 基础上，引入一个确定性的 guarded-generation layer。

这个版本的目标不是接入真实 LLM Provider，而是先把未来 LLM 报告生成所需要的约束、检查、回退和审计链路搭起来。

一句话概括：

> v0.6.1 的成果不是“LLM 会写报告”，而是“LLM 生成过程开始可约束、可检查、可回退、可审计”。

## 核心流程

```text
findings.json
→ constrained prompt
→ MockLLMProvider draft
→ RuleBasedSafetyChecker
→ checked LLM report or template fallback
→ safety_report.json
```

## validation.json 与 safety_report.json 的职责分工

### validation.json

`validation.json` 继续负责 artifact-level validation，也就是病例产物层面的完整性检查：

- required files 是否存在
- schema 是否有效
- required disclaimer 是否存在
- non-clinical use statement 是否存在
- human review requirement 是否存在
- deterministic artifact 是否可复现

它回答的问题是：

> 这个病例级 artifact 是否完整、结构是否有效、基础安全声明是否存在？

### safety_report.json

`safety_report.json` 负责 generation-level safety trace，也就是 LLM 草稿生成层面的安全审计：

- 使用的 provider
- mock mode
- raw draft 路径
- checked report 路径
- fallback 是否触发
- 被标记的不安全 claim
- 最终选择当前输出的原因
- 当前规则检查器的已知局限

它回答的问题是：

> LLM 原始输出是否越过 findings.json 的证据边界？如果失败，为什么触发 fallback？

## 安全决策策略

v0.6.1 采用保守的全局回退策略：

- 只要 RuleBasedSafetyChecker 检测到任意 unsafe claim，系统就不会尝试局部删除或改写 LLM 草稿，而是整体回退到 deterministic template report。
- `safety_report.json` 会记录所有被命中的风险类别和对应文本片段，用于审计和调试。
- 同一段文本如果同时违反多个安全边界，可以触发多条规则。这不是重复错误，而是为了保留多维度审计信息。
- v0.6.1 不做 partial repair，因为局部删改可能引入新的语义偏移；更安全的策略是完全回退。

## RuleBasedSafetyChecker 覆盖范围

RuleBasedSafetyChecker 不是完整 hallucination detector，也不声称能覆盖所有语义层面的幻觉。

它只是一个确定性的第一层安全门，主要覆盖本项目中高风险、可规则化识别的错误类型：

1. clinical diagnosis overclaim
2. CAM / heatmap overclaim
3. unsupported lesion localization
4. missing non-clinical-use disclaimer
5. missing human-review statement
6. image-quality overclaim

更细微的 semantic overclaim 暂时留给未来的 optional LLM-as-judge checker。

## v0.6.1 Provider 范围

v0.6.1 只实现确定性 Provider：

- TemplateProvider
- MockLLMProvider

暂不实现：

- OpenAIProvider
- ClaudeProvider
- local real LLM provider
- LLM-as-judge checker

## MockLLMProvider 模式

MockLLMProvider 用于可复现地测试 safety checker。

计划支持：

```text
safe
unsafe_diagnosis
unsafe_cam
unsafe_mixed
```

这些模式必须是 deterministic 的，方便在没有真实 LLM API 的情况下验证 guarded generation pipeline。

## 报告产物布局

v0.6.1 保留根目录 `report.md` 和 `report.html`，避免破坏 v0.6.0 的默认查看路径。

新增 `reports/` 目录保存中间产物和对照版本：

```text
experiments/case_reports/<case_id>/
├── report.md
├── report.html
├── reports/
│   ├── template.md
│   ├── template.html
│   ├── llm_raw.md
│   ├── llm_checked.md
│   └── llm_guarded.html
├── safety_report.json
├── validation.json
└── metadata.json
```

其中：

- `report.html` 始终代表最终选中的报告。
- `reports/template.html` 保存模板报告。
- `reports/llm_raw.md` 保存 MockLLMProvider 原始输出。
- `reports/llm_checked.md` 保存通过安全检查后的草稿。
- `reports/llm_guarded.html` 保存 guarded LLM HTML 报告。
- 如果 LLM draft 未通过安全检查，则 `report.html` 回退为模板报告。

## 可复现性说明

v0.6.1 只使用 deterministic mock providers，因此可以保持可复现。

真实 LLM Provider 暂缓到 v0.6.2，因为真实模型输出的可复现性需要记录：

- provider
- model version
- temperature
- top_p
- seed，如果 API 支持
- decoding metadata

部分 API 即使固定参数也不保证完全复现，因此 v0.6.2 需要单独处理 real LLM reproducibility notes。

## v0.6.1 明确不做的事

v0.6.1 暂不做：

1. 接入真实 LLM API
2. LLM-as-judge
3. Web demo
4. Docker deployment
5. 自动迁移旧 v0.6.0 case 目录
6. 复杂多轮报告编辑

## v0.6.1 阶段性成果

v0.6.1 做完后，项目应该新增以下能力：

1. constrained prompt construction
2. deterministic mock LLM report drafting
3. rule-based post-generation safety checking
4. explicit safety trace artifact
5. safe fallback to template report
6. visible generation status in report.html

对外描述：

> v0.6.1 introduces a deterministic guarded-generation layer on top of the v0.6.0 evidence-bottleneck case report prototype. It adds constrained prompt construction, mock LLM report drafting, rule-based post-generation safety checking, explicit safety trace artifacts, and safe fallback to the template report when unsafe claims are detected.
