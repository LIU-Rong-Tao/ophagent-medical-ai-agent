### 主要视觉与体验问题

1. **导航层级同形化**：工作区、模型工程、研究评测功能、评测模式和结果 Tab 大量使用相似的分段按钮。用户需要先读文字才能判断当前处于哪一层。
2. **全局首屏负担过重**：品牌标题、系统边界、四张全局 KPI 在多数任务页面重复出现，导致字段映射和审计结果常常在首屏下方才开始。
3. **模型资产与任务状态混杂**：上游资产数量、当前模态候选、Adapter、任务推理和路由资格在同一区域并列，容易把“已登记”理解成“可运行”。
4. **卡片语义重复**：同一页面同时使用全局 KPI、局部 KPI、状态卡、说明卡和折叠卡，视觉重量接近，难以判断哪些是结论、哪些是入口。
5. **研究条件出现太晚**：主版本、标签空间、数据 split、代理事件边界等研究条件分散在控件和说明文字中，没有先形成冻结上下文。
6. **字段映射纵向过长**：上传、原始表预览、基础字段、版本字段、概率列和阈值都顺序铺开。两个以上 variant 时首屏无法形成完整流程心智模型。
7. **表格阅读成本偏高**：Streamlit 默认 DataFrame 样式与自定义状态卡视觉不统一；长列名、风险标签和 59 类行会挤压扫描空间。
8. **图表拥挤或空白感明显**：图表、表格和解释在单列中连续堆叠；低方差分布会产生大面积空图，固定预算表又过宽。
9. **59 类场景缺少默认阅读策略**：完整 59×59 混淆矩阵和 59 行分类指标不适合作为默认视图。应默认 Top 混淆方向、类别聚焦和长尾筛选，并保留完整下载。
10. **技术状态与研究结果混在同一叙事**：Adapter、checkpoint、生成任务和离线审计资格会出现在研究指标附近，负责人容易误认为离线结果已完成在线接入。
11. **页面风格不完全统一**：自定义品牌/KPI、Streamlit 原生控件、Altair 图表、DataFrame 和 dialog 各自有不同边框、间距和文字密度。
12. **窄窗口只能“压缩”，没有“重排”**：分段导航、KPI 和宽表主要依靠换行或横向滚动，核心信息没有按优先级改为纵向摘要。

当前病例 dialog 的“左图、右侧三张模型结果卡、下方路由依据”结构是成立的，正式重构应保留；需要优化的是卡片层级、匿名标识和窄窗口重排，而不是推翻该结构。

## 4. 方案 A：临床工作站风

入口：[静态原型](option_a_clinical_workstation/index.html) · [截图目录](option_a_clinical_workstation/screenshots/)

### 设计规则

| 项目 | 决策 |
|---|---|
| 页面布局 | 218px 深色固定侧栏 + 紧凑顶栏 + 高密度工作区 |
| 导航 | 持久左侧树状分组；当前项用左侧色条和深色面突出 |
| 最大宽度 | 1540px，适合 1440–1920px 工作站显示器 |
| 色彩系统 | 深海军蓝侧栏、白/冷灰数据面、克制蓝主色；红/黄/绿仅用于状态 |
| 背景与分区 | 冷灰背景；依靠细边框和表头区分，不依赖阴影 |
| 字体层级 | 23px 页面标题、17px 区块标题、14px 正文、11–12px 元数据 |
| 间距系统 | 4/8px 基础节奏；页面间距 16/20/24px，组件内部更紧凑 |
| KPI | 六列连续状态条，几乎无圆角；异常项用左边框而非整卡染色 |
| 表格 | 高对比表头、8px 行内距、数字右对齐、状态列固定宽度 |
| 状态标签 | 近矩形小标签，颜色 + 圆点 + 文字三重表达 |
| 图表 | 优先横向排名、阈值线和表格联动；不使用装饰动画 |
| 主/次按钮 | 深蓝实心主按钮、白底描边次按钮；每屏最多一个主要动作 |
| 上传与映射 | 同屏左右分栏；左侧映射，右侧持续显示校验摘要 |
| 空状态 | 直接说明缺少什么及下一步动作，不展示插画 |
| 错误状态 | 红色细边框 + 原因 + 恢复动作；不整页铺红 |
| 加载状态 | 固定高度骨架或进度行，避免表格跳动 |
| 窄窗口 | 侧栏转横向滚动导航；KPI 两列；表格转字段化记录卡 |

### 优点

- 最适合高频模型资产核对、接入门控和病例列表扫描。
- 技术状态层级最清楚，能够压制“AI SaaS 卡片感”。
- 表格密度高，在 59 类与多 checkpoint 场景下效率最好。

### 缺点

- 研究报告的叙事感较弱，组会截图可能显得偏运维。
- 深色侧栏在 Streamlit 中需要更谨慎处理原生控件和主题同步。
- 对首次使用者不如方案 C 友好，需要清晰默认入口。

### 实施成本与预计范围

- 成本：中等。
- 主要涉及 `app/model_hub_ui.py` 的设计令牌/表格/状态标签、`app/model_hub_demo.py` 的导航壳，以及工程/病例页面的信息重排。
- 无需改动后端和指标，但要把当前多个 KPI 组件统一为一套紧凑组件。

## 5. 方案 B：研究分析台风

入口：[静态原型](option_b_research_console/index.html) · [截图目录](option_b_research_console/screenshots/)

### 设计规则

| 项目 | 决策 |
|---|---|
| 页面布局 | 顶部研究导航 + 1320px 居中报告画布；页面按协议、指标、证据展开 |
| 导航 | 横向页签式导航，强调当前研究视图而不是系统模块 |
| 最大宽度 | 1320px，控制图表和长文本行宽 |
| 色彩系统 | 浅灰偏暖背景、低饱和蓝绿主色、琥珀与砖红作为研究提示 |
| 背景与分区 | 大面积无框画布 + 细分隔线；减少离散卡片 |
| 字体层级 | 标题使用系统衬线替代，数据和正文仍使用无衬线；强调“报告章节” |
| 间距系统 | 8px 基础节奏；区块间 24–32px，方法说明与指标之间留出呼吸 |
| KPI | 无浮层、底边分隔，像论文结果摘要而非运营仪表盘 |
| 表格 | 表头小型大写、指标列等宽数字、说明列保留研究口径 |
| 状态标签 | 低饱和矩形标签，不抢图表主视觉 |
| 图表 | 主图 + 一句结论 + 方法边界；统一图例和下载入口 |
| 主/次按钮 | 低饱和绿色主按钮、细描边次按钮 |
| 上传与映射 | 明确四步流程；映射区与“校验预览/资格边界”并排 |
| 空状态 | 以“尚无结果 / 需要哪些输入”作为研究记录空页 |
| 错误状态 | 区分数据错误、协议警告和当前无法评估，不混成一个红色错误 |
| 加载状态 | 章节级骨架，保留标题与研究上下文 |
| 窄窗口 | 顶部导航横向滚动；报告区单列；图表先显示结论再显示图形 |

### 优点

- 最适合组会汇报、指标解释、方法局限和风险审计叙事。
- 能把“临床后果尚未评估”“公开标签代理”等边界放在正确层级。
- 59 类默认 Top 混淆 + 类别聚焦的呈现最自然。

### 缺点

- 顶部横向导航模块较多，窄窗口需要二级菜单或滚动。
- 模型资产和接入状态页面不如方案 A 高效。
- 系统衬线标题在不同服务器字体环境下存在轻微渲染差异。

### 实施成本与预计范围

- 成本：中等偏高。
- 主要改动集中在 `app/model_hub_research.py`、`app/model_hub_result_audit.py` 和统一图表/方法说明组件。
- 若要求完全一致的字体，需要静态字体资产；不建议为 Streamlit 强行引入远程字体。

## 6. 方案 C：现代模型中转台风

入口：[静态原型](option_c_modern_model_hub/index.html) · [截图目录](option_c_modern_model_hub/screenshots/)

### 设计规则

| 项目 | 决策 |
|---|---|
| 页面布局 | 242px 浅色侧栏 + 顶部环境状态 + 1450px 响应式工作区 |
| 导航 | 资产、接入、研究、回放形成一套持久导航；入口路径最清楚 |
| 最大宽度 | 1450px，在流程清晰与表格容量间折中 |
| 色彩系统 | 白/冷灰底、深文字、青绿主操作、蓝/琥珀/红语义色 |
| 背景与分区 | 轻量卡片与全宽表格并用，阴影只保留一级 |
| 字体层级 | 27px 页面标题、17px 区块标题、14px 正文、12px辅助信息 |
| 间距系统 | 8px 基础节奏；页面 24/28px、区块 16/24px |
| KPI | 独立轻卡，关键异常增加顶部色条；最容易快速浏览 |
| 表格 | 适中行高、状态胶囊、清晰操作列 |
| 状态标签 | 圆点 + 文本的轻胶囊，强调可读性而非装饰 |
| 图表 | 清晰图表卡 + Top-N 筛选 + 解释条 |
| 主/次按钮 | 青绿色主按钮，描边次按钮，命令层级明显 |
| 上传与映射 | 产品化四步流程；上传、映射、校验摘要同时可见 |
| 空状态 | 保留流程位置并给出唯一下一步动作 |
| 错误状态 | 就地提示原因和修复动作；保留返回上一步 |
| 加载状态 | 稳定尺寸骨架和进度状态，不改变布局 |
| 窄窗口 | 侧栏变顶部导航，KPI 两列，表格转记录卡，步骤器纵向排列 |

### 优点

- 整体产品路径最清楚，新用户最容易理解“资产 → 接入 → 评测 → 回放”。
- 与现有 Streamlit 结构兼容度最高，渐进式实施风险最低。
- 视觉比当前统一，同时不会变成营销站或浮夸 AI 页面。

### 缺点

- 若所有页面都使用独立 KPI 卡，仍可能重新出现卡片过多的问题。
- 表格密度和研究叙事分别不如 A、B 的专长。
- 需要严格限制圆角、阴影和状态色，否则容易滑回通用 SaaS 风格。

### 实施成本与预计范围

- 成本：中等偏低。
- 可主要通过 `app/model_hub_demo.py`、`app/model_hub_ui.py` 和页面级布局调整渐进实现。
- 现有业务函数、结果 DataFrame 与图表数据接口可直接复用。

## 7. 推荐混合方案

推荐采用：

- **整体导航与操作流程：方案 C**
- **模型资产、接入状态和病例清单：方案 A**
- **风险审计图表、方法说明和 59 类阅读策略：方案 B**

关键页面样例：

- [风险审计总体表现](recommended_hybrid/screenshots/overview.png)
- [模型资产目录](recommended_hybrid/screenshots/assets.png)
- [病例清单](recommended_hybrid/screenshots/cases.png)

### 推荐理由

OphAgent 同时承担三种工作：模型资产管理、任务级准入门控和研究结果解释。单一视觉范式很难兼顾：

- 纯 A 会把研究结果做得像运维报表；
- 纯 B 会降低模型接入和高频列表效率；
- 纯 C 最平衡，但表格密度和科研方法层级仍不够有辨识度。

混合方案不是把三套样式随意拼接，而是按内容类型分工：系统壳保持 C 的一致性，操作型数据面采用 A 的密度，证据型页面采用 B 的阅读顺序。推荐将它作为正式重构的方向。

## 9. Streamlit 可行性判断

### 可以稳定实现

- 集中 CSS 设计令牌、统一边框/圆角/间距/状态色。
- 侧栏或顶层工作区导航，以及页面级面包屑。
- 紧凑 KPI 条、状态标签、接入矩阵和分组表格。
- `st.file_uploader` + 四步流程提示 + 双栏字段映射。
- 使用 Altair/Plotly 实现 Top 混淆、固定预算曲线、筛选和下载。
- 59 类时默认 Top-N、类别选择和完整 CSV 下载。
- `st.dialog` 中保持“左图、右结果、下方依据”的病例结构。
- 390/768/1024/1440 断点下的列数变化、表格列收敛和步骤器纵排。
- 空状态、错误状态、加载骨架和明确恢复动作。

### 不建议强行实现

- 依赖 Streamlit 私有 DOM 层级的复杂 sticky 多级表头；版本升级容易失效。
- 在一个页面中同时固定侧栏、顶栏、Tab 和表头四层滚动区域。
- 纯 CSS 模拟完整前端路由转场和大规模微动画。
- 直接在页面渲染 59×59 全混淆矩阵并要求每格可读。
- 把 50+ 行病例表强行改成自制虚拟列表；优先使用分页和筛选。
- 仅靠 hover 承载公式、方法边界或审计解释；重要信息必须可点击或常驻。
- 为追求截图一致性引入远程字体、玻璃效果、发光、蓝紫渐变或复杂阴影。

## 10. 原型状态覆盖

三套方案在设计规则中均定义了空、错误和加载状态；关键业务页面展示了正常状态。正式实现时应把状态做成复用组件，而不是在每页单独写 CSS。当前静态原型的导航可点击，但按钮、上传和选择框均不连接业务逻辑。
